# AI Agent 賞金狩獵工作流程 v4.2
## 雙主軸：理解深度 × 幻覺清零

> 核心信念：**幻覺同理解深度係同一件事嘅兩面。**
> 幻覺 = 冇證據嘅自信。深度 = 有證據嘅預測。
> 所以成個流程只有一條鐵律：**每一句關於系統嘅陳述，都要分得清係「觀察」定「推斷」。**

---

## 第一部：幻覺清零系統（HALLUCINATION FIREWALL）

### 1.1 AI 喺安全研究嘅五大幻覺源（先認清敵人）

| 幻覺源 | 典型表現 | 後果 |
|---|---|---|
| **H1 發明資產** | 報告一個從未真實請求過嘅 endpoint/參數 | 報告秒殺，信譽歸零 |
| **H2 誤讀回應** | 見到 500 就話係 RCE、見到反射就話係 XSS | 假陽性轟炸（Google 封殺 AI 報告嘅原因） |
| **H3 虛構因果** | 「因為 A 所以 B」——但冇排除其他解釋 | 結論錯，方向全錯 |
| **H4 假裝重現** | 報告寫「已重現」但係基於一次觀察或推理 | 違反計劃規則，等同欺詐 |
| **H5 記憶混淆** | 將目標 A 嘅行為套落目標 B、將 writeup 嘅嘢當成自己觀察 | 模型污染，越轉越錯 |

### 1.2 鐵律：觀察 vs 推斷 標籤制度

**Agent 輸出嘅每一句關於系統嘅陳述，必須帶標籤：**

```
[OBS] 觀察：有原始證據（request/response 原文、code 行號、文檔連結）
      → 必須附證據引用，證據唔存在 = 呢句嘢唔准存在
[INF] 推斷：由觀察推理出嚟嘅假設
      → 必須寫明「基於邊幾條 OBS」
[HYP] 假設：未驗證嘅猜想
      → 唔准用肯定語氣，唔准入報告
```

**執行規則：**
- 寫入模型文件（D1/D2/D3）嘅嘢，**只准係 [OBS] 或 [INF]**；[HYP] 只可以活喺假設清單
- 每條 [OBS] 附證據指針（檔案+行號 / request ID）；**無指針嘅 [OBS] 自動降級為 [HYP]**
- 每條 [INF] 列明依賴嘅 [OBS] 編號——依賴鏈斷咗（某條 OBS 被推翻），所有下游 [INF] 自動標記「待覆核」

### 1.3 三重驗證閘（任何「命中」出閘前必過）

```
第一重：證據閘（自己）
  □ 每一步觀察有原始 request/response 原文？
  □ 截圖/日誌係咪由工具產出，唔係由「我記得」產出？
  □ 報告中每個技術陳述都可以指出證據？

第二重：對抗閘（質疑者實例）
  獨立推理實例，任務係**推翻**：
  - 「呢個行為用正常功能可唔可以解釋？」
  - 「有冇第三個解釋（cache、負載平衡、自己 session）令結論唔成立？」
  - 「影響係咪真係跨咗安全邊界，定係自己郁自己？」
  - 「重現步驟係咪依賴觀察者嘅特殊狀態？」
  → 質疑者提出嘅每條反駁，必須用實驗（唔係用推理）回應

第三重：空白閘（fresh-context 重現）
  一個**全新 context、冇睇過任何先前推理**嘅實例，
  淨係攞住重現步驟文件，逐步執行：
  → 跟唔到 = 步驟有隱藏假設 = 報告未合格
  → 呢一關專殺「因為我寫嘅所以我以為我寫得清楚」
```

### 1.4 幻覺事故處理
- 任何時候發現模型入面有一條 [OBS] 係假嘅 → **幻覺事故**，即時：
  1. 標記該條目 + 追溯所有依賴佢嘅 [INF]/[HYP]，全部降級覆核
  2. 寫入 `hallucination_log.md`：邊個環節產生、點解冇攔到
  3. 每週統計幻覺率，納入 KPI（見 3.2）

## 第二部：理解深度引擎（DEPTH ENGINE）

### 2.1 深度公式
```
深度 = 預測力 × 描述維度數 × 被推翻次數
```
三個乘數都係**可量化、可追蹤**嘅——深度唔再係感覺，係數字。

### 2.2 三份描述並行建模
| 描述 | 內容 | 來源 | 幻覺防控 |
|---|---|---|---|
| D1 文檔版 | 設計意圖 | 官方文檔 | 每條附文檔 URL+章節 |
| D2 代碼版 | 實際邏輯 | 開源 repo | 每條附 repo+檔案+行號 |
| D3 流量版 | 運行時行為 | Burp 實錄 | 每條附 request ID |

### 2.3 建造者視角推導
```
對每個核心功能：
1. 遮住實作：「根據 D1，如果我實現，會點設計？」寫低預測
2. 對照 D2/D3
3. 推導錯 → 理解缺口 或 實作古怪（兩者都追）
```
> 呢個工序同時係深度引擎**同**幻覺檢測器：推導錯而實作正常 = 你嘅模型有幻覺成分。

### 2.4 三個深化工序（每輪循環必過）
1. **矛盾狩獵**：D1/D2/D3 互相 diff，每個矛盾 → 「暗示咗咩 → 可測試假設」
2. **異常追問**：每個異常必填「呢個暗示嘅內部結構係___」，冇填唔准做下一個動作
3. **生命週期抽檢**：每週抽一個 data item 畫完整生命週期，斷點 = 理解嘅洞 = 下輪目標

### 2.5 深度階梯自檢（每週評一次自己企喺邊層）
| 層次 | 標誌 |
|---|---|
| L1 描述 | 講到佢做乜 |
| L2 預測 | 未試已知結果 |
| L3 解釋 | 知點解咁設計 |
| L4 重構 | 俾你寫你會點寫，知 trade-off |
| L5 預見缺陷 | 設計層已見到邊度會爛——漏洞自己凸出嚟 |

## 第三部：執行循環（兩引擎驅動嘅主流程）

```
BUILD MODEL（三描述建模，全 [OBS]/[INF] 標籤）
   → DEEPEN（矛盾狩獵 + 異常追問 + 建造者推導）
   → FIND GAPS（12 條質詢 → [HYP] 假設 + 預測訊號）
   → PROBE（最小請求驗證）
        ├─ 中 → 三重驗證閘 → 人類批准 → 報告
        └─ 唔中 → 模型修正記錄（深度+1）→ 回流
```

### 3.1 落差質詢清單（12 條，不變）
信任邊界 3 條（權限層跳過／上游信任／tenant 隔離）、意圖落差 3 條（流程跳步／值可改／上游 validate 漏）、狀態 2 條（TOCTOU／撤銷後殘留）、交互 2 條（A 輸出= B 輸入／功能碰撞）、AI 產品 2 條（可讀範圍 vs 應見範圍／工具權限級別）。

### 3.2 雙軸 KPI（每週）
| 深度軸 | 幻覺軸 |
|---|---|
| 預測訊號命中率（目標 >30% 持續上升） | **幻覺率**：被推翻嘅 [OBS]/[INF] ÷ 總陳述（目標 <5% 持續下降） |
| 每週矛盾發現數 | 三重閘攔截數（第幾重攔到——越前攔到越健康） |
| 模型修正次數 | 幻覺事故數（目標 0） |
| 可重用信任邊界模式數 | 空白閘一次通過率（報告質量嘅終極指標） |

> **兩軸嘅關係**：深度升而幻覺率唔降 = 模型越嚟越自信嘅錯；幻覺率降而深度唔升 = 太保守唔敢推斷。**兩軸同時改善先係健康。**

### 3.3 撤離判斷
- 12 條質詢問晒 + 連續 2 週無新矛盾 → 目標熟咗，轉場
- 幻覺率連續 2 週 >15% → **停低，唔好轉場**——問題唔係目標，係你嘅方法；檢討幻覺源先

## 第四部：CVE 變種分析 —— 主線策略（v4.2 起升級為主力）

> 策略定位：**CVE 跟隨係主線，模型驅動係支援。**
> 每條泳道嘅預設起點唔再係「由零建模」，係「由最新嘅 GOLD 級 CVE 出發」——
> root cause 即刻俾你三份描述嘅種子，建模成本大跌；模型驅動嘅三份描述、
> 矛盾狩獵、三重閘全部保留，但係用嚟**深挖 CVE 嘅變種**，唔係冷啟動。
> Patch 係藏寶圖；我哋搵嘅係地圖上未標記嘅 X。

### 4.1 揀 CVE 嘅標準（唔係個個都跟）
- **GOLD**：有 root cause + commit diff + 可泛化錯誤 pattern + 喺泳道範圍內 → 全力跟
- **SILVER**：有 root cause 但細節有限 → 留意
- **SKIP**：只有一句描述 / 唔喺範圍 / 明星 CVE（萬人跟嘅紅海，避開）

### 4.2 每週例行工序
1. 週一掃上週 MSRC Security Update Guide + Chrome/Android security bulletin
2. 揀 1–2 個同泳道相關嘅 CVE，root cause 寫入 ModelStore D2_code（證據指針 `cve:CVE-XXXX-XXXXX@commit`）
3. 衍生三個標準變種假設：
   - 同 pattern 喺同 codebase 其他 function 重複出現？
   - 同 pattern 喺姊妹產品/相鄰組件出現？
   - 官方 patch 係咪只修咗觸發路徑 A，路徑 B/C 仲到達到同一個 sink？
4. 每個月對比：CVE 衍生假設命中率 vs 一般假設——數字話你知呢條路啱唔啱你

### 4.3 暗湧警告
- 黃金窗口係公佈後幾日到幾週；duplicate 率極高，速度係一切
- CVE 係加速器唔係全部：唔跟 CVE 嘅地方反而少人耕
- 代碼實現：`agent/cve_feed.py`（CveRecord 質量分級 → ingest 入模型 → 衍生變種假設）
